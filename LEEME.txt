 QUE TRAE LA PARTE 5
--------------------------------------------------------------------------------

 LO QUE NO PUEDE HACER (dicho antes que nada)
   El codigo corre en un equipo que controla el cliente. Quien sepa de Node y
   tenga acceso de administrador puede abrir middlewares/licencia.js, borrar
   dos lineas y saltarselo todo. Le pasa a CUALQUIER sistema de licencias del
   lado del cliente, incluidos los comerciales de pago.
   El objetivo realista, que si se cumple: que copiar la instalacion y
   manipular la hora no funcionen, y que todo intento quede registrado.

 INMUNIDAD A LOS CAMBIOS DE HORA
   No se usa el reloj del equipo. Se usa un trinquete que SOLO AVANZA:

     tiempo_confiable = MAXIMO de:
        - el reloj del sistema
        - el trinquete ya guardado
        - LOS DATOS DEL NEGOCIO: ultima venta, ultimo cierre de turno,
          ultimo asiento de auditoria, ultimo movimiento de inventario
        - la hora de un servidor externo, si hay internet (oportunista)

   La tercera fuente es la clave: para "recuperar" tiempo habria que borrar las
   ventas, los cierres de caja y la auditoria, o sea destruir la contabilidad
   que el negocio necesita. El propio uso del sistema prueba el tiempo pasado.

   Ademas se cuentan DIAS NATURALES DISTINTOS con actividad: atrasar el reloj
   repite el mismo dia y no suma; adelantarlo quema los dias mas rapido.

 INMUNIDAD A LA COPIA FISICA
   Huella del equipo PONDERADA y tolerante (no un hash rigido):

     Mismo equipo .................. 100%  funciona
     Tarjeta de red nueva ...........  80%  funciona (queda anotado)
     Mas memoria / renombrar equipo .  72%  funciona
     Otro equipo ....................   8%  BLOQUEA

   Se exige 70%. Ningun componente vale por si solo mas que el umbral.
   Ademas la licencia esta atada a un UUID de instalacion en la base de datos.

 RESTAURAR UN RESPALDO ANTIGUO
   El estado se replica FUERA de la base (licencia/estado.dat) y siempre gana
   el valor mas avanzado:
     - Restauras la BD  -> el archivo conserva el contador
     - Borras el archivo -> la BD lo conserva
     - Borras los dos    -> los datos del negocio siguen probando el tiempo
     - Editas por SQL    -> el sello HMAC de la fila no cuadra y se detecta

 BLOQUEO ESCALONADO (no tumba el servicio)
     NO CONFIGURADA  sistema dormido, no restringe nada
     ACTIVA          todo normal
     GRACIA (7 dias) todo funciona, solo se avisa a administracion
     BLOQUEADA       no se abren turnos ni comandas nuevas, PERO si se puede
                     cobrar las cuentas abiertas, cerrar el turno e imprimir

--------------------------------------------------------------------------------
 ACTIVAR LAS LICENCIAS (OPCIONAL, solo el proveedor)
--------------------------------------------------------------------------------

 A. Generar el par de claves, UNA SOLA VEZ, en TU equipo:
      node scripts/licencia-emitir.js claves
    -> licencia-privada/licencia.key  LA CLAVE PRIVADA. Nunca sale de tu equipo.
       licencia-privada/licencia.pub  se copia a config/licencia.pub del cliente

    CRITICO: guarda licencia.key fuera del repositorio y con respaldo. Si la
    pierdes no podras renovar licencias ya desplegadas. Si se filtra, cualquiera
    podra emitirlas.

 B. El cliente genera su solicitud (sin internet):
      node scripts/licencia-solicitar.js --cliente "Restaurante Bahia"
    Muestra un codigo dictable por telefono, p.ej. P23DF-45KE8-SHWMU-H579P
    (sin caracteres que se confundan: ni 0/O ni 1/I/L)

 C. Tu emites la licencia:
      node scripts/licencia-emitir.js emitir \
           --solicitud solicitud-licencia.json \
           --cliente "Restaurante Bahia" --plan PROFESIONAL \
           --dias 365 --gracia 7 --salida licencia.lic

      Opciones: --perpetua | --dias-uso 300 | --funciones pos,inventario,...

 D. El cliente instala:
      copiar el archivo a licencia/licencia.lic
      o pegar su contenido en /admin/licencia
      y copiar la clave publica a config/licencia.pub  <- el interruptor

 Diagnostico en cualquier momento:
      node scripts/licencia-estado.js
      node scripts/licencia-estado.js --red

 ANTES DE DESPLEGAR - EJECUTA ESTAS CONSULTAS
--------------------------------------------------------------------------------

 1) Platillos que dejaran de descontar (defecto del ID cruzado ya corregido):

    SELECT pm.id, pm.nombre
      FROM platillos_menu pm
      LEFT JOIN recetas r ON r.platillo_id = pm.id AND r.activa = 1
     WHERE r.id IS NULL
     ORDER BY pm.nombre;

 2) Insumos sin ficha de costo, por impacto:

    SELECT p.id, p.nombre, COUNT(DISTINCT rd.receta_id) AS recetas
      FROM receta_detalles rd
      INNER JOIN productos p ON p.id = rd.producto_id
      LEFT JOIN fichas_costo_producto f ON f.producto_id = p.id AND f.vigente = 1
     WHERE f.id IS NULL
     GROUP BY p.id, p.nombre ORDER BY recetas DESC;

 3) Tras migrar, que no quede ningun token en claro:

    SELECT COUNT(*) total,
           SUM(CASE WHEN CHAR_LENGTH(token) <> 64 THEN 1 ELSE 0 END) en_claro
      FROM usuarios_tokens;   -- en_claro debe ser 0

--------------------------------------------------------------------------------
 LO MAS URGENTE QUE SIGUE PENDIENTE
--------------------------------------------------------------------------------

 El archivo .env con la contrasena de la base de datos y los secretos de sesion,
 junto con certs/key.pem, SIGUEN PUBLICADOS en el historial de GitHub. Cualquiera
 puede clonar el repositorio y, con el SESSION_SECRET expuesto, falsificar
 sesiones directamente. Proteger el software con licencias mientras las
 credenciales estan publicas es poner la alarma y dejar la llave puesta.
 Rotar esas credenciales y anadirlas a .gitignore es hoy la tarea mas urgente.
